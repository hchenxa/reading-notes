# Istio 升级中断排查:为什么 patch label 会断而翻 tag 不会

> 资料核对日期:2026-09-27。源码基准 `istio/istio@9c8ba31`(master,sparse clone)。
> 本文讨论的是**多 revision + Gateway API** 场景下,`1.30.2 → 1.30.3` 这种**两侧控制面都已带修复**
> 的升级里仍然出现的约 30 秒连接中断。那个 bug 本身的根因见 [Gateway 配置清空 Bug](Gateway配置清空Bug.md)。

## 0. 结论速览

- **两种操作不等价。** 但差异**不在"所有权判定"这一层** —— `IsMine` 确实把 tag 名和 revision 名
  当同一类值比较,那一层完全等价。
- 差异在于**实际写入的对象集合**:patch label 会连锁改写 **6 个**生成对象(含 **LoadBalancer
  Service**),翻 tag 只改写 **1 个**(Deployment 的 pod template),其余 5 个内容逐字节相同、
  SSA re-apply 等于 no-op。
- 因此 patch label 时,「**入口对象被改写**」与「**Pod 滚动**」两个扰动窗口叠加;翻 tag 时只有
  后者。
- **但这条链的最后一步尚未验证** —— 究竟哪次写入是直接原因,见 §4,有两个可以直接跑的实验。

## 1. 两组对比实验

环境:多 revision 并存多个 istiod(`1.30.0` / `1.30.2` / `1.30.3` …),ingress 使用 Kubernetes
Gateway API 的 `Gateway` 资源 + istio 的 `GatewayClass`。观测手段是 Gateway 前面挂 LB,
循环 curl 打 LB 地址,记录失败窗口。

| | **方式 A:patch label** | **方式 B:翻 tag** |
| --- | --- | --- |
| Gateway 的 `istio.io/rev` | `1.30.0` → patch 成 `1.30.2` → patch 成 `1.30.3` | 恒为 `stable`,整个生命周期不变 |
| 切换动作 | `kubectl patch` Gateway label | `istioctl tag set stable --revision 1.30.2` → `--revision 1.30.3` |
| 1.30.0 → 1.30.2 | 约 30s 中断 | — |
| **1.30.2 → 1.30.3** | **约 30s 中断** | **无中断** |

**表格最后一行是本文要解释的核心问题。** `1.30.2 → 1.30.3` 两侧的 istiod 都已经带了
[Gateway 配置清空 Bug](Gateway配置清空Bug.md) 的修复(1.29.5 / 1.30.2 / 1.31.0+),
所以那个"旧控制面把 Gateway 剔除、推空 xDS"的根因**在这一步并不成立** —— 中断另有来源。

两种方式的共同现象:Gateway 对应的 Deployment 都**正常滚动**,新 Pod 也能正常起来。
差异在于方式 A 在滚动窗口内有约 30 秒的连续失败。关键特征是"新 Pod 是好的,老 Pod 也没崩,
但流量就是断的"。

## 2. 等价的部分:所有权判定

`pkg/revisions/tag_watcher.go`:

```go
func (p *tagWatcher) GetMyTags() sets.String {
    res := sets.New(p.revision)                          // 自己的 revision 永远算自己的
    for _, wh := range p.webhooksIndex.Lookup(p.revision) {
        res.Insert(wh.GetLabels()[label.IoIstioTag.Name]) // 再加上所有指向自己的 tag 名
    }
    // ... servicesIndex 同理
    return res
}

func (p *tagWatcher) IsMine(obj metav1.ObjectMeta) bool {
    selectedTag, ok := obj.Labels[label.IoIstioRev.Name]  // "canary" 或 "1-30-2"
    // ... 无 label 时回退到 namespace 的 istio.io/rev
    return p.GetMyTags().Contains(selectedTag) || /* default tag 的特殊分支 */
}
```

`myTags` 是「自己的 revision ∪ 指向自己的 tag」,两者是**同一类值**,没有任何优先级或宽容度差别。
把 label 写成 `canary`(tag)还是 `1-30-2`(revision 名),对 `IsMine` 而言完全一样。

**但要注意这个等价的边界**:它只说明"谁拥有 Gateway"翻转方式相同,**不代表两个操作等价**。

另一个前提也要先确认:**两种方式下,gateway Deployment 的 pod template 都会变、都会滚动**。
因为 tag 从不进入 Pod spec —— `CA_ADDR` 取的是 owner istiod 自己的 revision:

```yaml
# manifests/charts/istio-control/istio-discovery/files/kube-gateway.yaml
- name: CA_ADDR
  value: istiod{{- if not (eq .Values.revision "") }}-{{ .Values.revision }}{{- end }}.{{ .Values.global.istioNamespace }}.svc:15012
```

所以差别不在"滚不滚",而在**滚动之外还改了什么**。

## 3. 不等价的部分:两种操作写入的对象集合

关键在于 `PILOT_ENABLE_GATEWAY_API_COPY_LABELS_ANNOTATIONS` **默认为 true**
(`pilot/pkg/features/experimental.go:152`),它会执行 `maps.Clone(gw.GetLabels())` ——
把 Gateway 的 `metadata.labels` **原样复制到它生成的所有对象上**。`.InfrastructureLabels`
出现在 `kube-gateway.yaml` 的 6 处 labels:

| 行号 | 对象 |
| --- | --- |
| L10 | ServiceAccount |
| L33 | Deployment `metadata.labels` |
| L66 | **Pod template labels** |
| L328 | **Service(`type: LoadBalancer`)** |
| L365 / L391 | HPA / PDB |

### 3.1 方式 A:patch Gateway 的 label

```
  你 ──kubectl patch──▶ Gateway.metadata.labels
                          istio.io/rev: 1.30.2 → 1.30.3
        │
        │ ① label 被复制出去
        │    InfrastructureLabels = maps.Clone(gw.GetLabels())
        ▼
  istiod 写入 6 个生成对象,全部真实变化:
        ServiceAccount   metadata.labels        ✎
        Deployment       metadata.labels        ✎
          └ Pod template   labels                ✎  (istio.io/rev 只可能来自这里)
        Service (LB!)    metadata.labels        ✎  ← 流量入口对象
        HPA              metadata.labels        ✎
        PDB              metadata.labels        ✎
          └ Pod template 的 rev 注解 / CA_ADDR / image 也变
        ▼
  Deployment 滚动  +  5 个对象 metadata 被改写   ← 两个扰动叠加
```

### 3.2 方式 B:翻 tag

```
  你 ──istioctl tag set stable --revision 1.30.3──▶ istio-system 里两个对象
        MutatingWebhookConfiguration istio-revision-tag-stable
        Service istiod-stable
        (Gateway 对象「完全不被任何写入者触碰」)
        │
        │ ② tagWatcher 重算 GetMyTags()
        ▼
  istiod-1.30.3: IsMine(Gateway) = true
  istiod-1.30.2: IsMine(Gateway) = false
        │
        ▼
  istiod 写入同样的 6 个对象,但其中 5 个内容逐字节相同 → SSA no-op
  只有 Deployment 的 pod template 真正变化:
        ├ labels      不变(恒为 stable)
        ├ rev 注解    1.30.2 → 1.30.3
        ├ CA_ADDR     变
        └ image       变
        ▼
  只有 Deployment 滚动                            ← 单一扰动
```

### 3.3 对照表

| | 方式 A(patch label) | 方式 B(翻 tag) |
| --- | --- | --- |
| Gateway 对象本身 | **被用户改写**(resourceVersion 变,唤醒所有 Gateway watcher) | 从不被碰 |
| Deployment pod template 的 rev 注解 / `CA_ADDR` / image | 变 | 变 |
| Deployment pod template 的 **labels** | **变**(1.30.2 → 1.30.3) | 不变(恒为 `stable`) |
| **Service(LB)metadata.labels** | **变** | **不变** |
| ServiceAccount / HPA / PDB labels | **变** | **不变** |
| 内容真正变化的生成对象数 | **6 个全变** | **只有 1 个** |

> 补充一个代码事实:istiod **从不修改 Gateway 的 label**。它唯一写 Gateway 的地方是
> `deploymentcontroller.go:779`(`setGatewayControllerVersion`),且只在从旧 controller-version
> 接管时写一次注解。所以方式 A 里 Gateway label 的变化,只可能来自你自己的 patch。

## 4. 哪一次写入导致了连接中断

差异集合只有 4 项,逐个判断它们能不能作用到"连接"上:

| # | 只有方式 A 发生的写入 | 能否直接作用于连接 | 判断 |
| --- | --- | --- | --- |
| 1 | Gateway 对象本身被改写 | 唤醒集群里所有 Gateway watcher。istio 自身**不会**因此断流(配置已不分 revision) | 放大器,不是直接原因 |
| 2 | **Service(`LoadBalancer`)metadata.labels 被改写** | **会** —— 它是流量入口对象,是唯一被改写的入口资源 | **首要嫌疑** |
| 3 | Pod template 的 `istio.io/rev` label 从 `1.30.2` 变 `1.30.3` | 只有当集群里有东西**以该 label 为选择器**时才会(NetworkPolicy / 自研 controller / 监控抓取规则)。istio 自身不按它选 Pod | 需要自查 |
| 4 | ServiceAccount / HPA / PDB 的 metadata.labels 被改写 | 无直接影响 | 排除 |

**必须诚实标注置信度**:

- **已确定(代码直读)**:上面的写入集合差异。方式 A 真实改写 6 个对象,方式 B 只改写 1 个。
- **未确定**:第 2 项是否就是那 30 秒的直接原因。metadata-only 的 Service 更新对多数 LB 控制器
  (含 AWS CCM)是 no-op —— 所以单靠它解释 30 秒**偏弱**,但在 kind + cloud-provider-kind 环境里
  必须实测。第 3 项取决于你自己集群里有什么东西按 `istio.io/rev` 选 Pod。

`30s` 这个数字本身也是个线索:它同时吻合 `startupProbe` 的预算(30×1s)、以及
`terminationGracePeriodSeconds` 的 k8s 默认值 30s。所以更可能的形态是
**「入口对象被改写」与「Pod 滚动」两个窗口叠加**,而不是某个单一对象。

### 4.1 决定性实验一:把 label 复制链关掉

既然差异已经定位到这条复制链,就直接把它切断:

```bash
# 给 istiod 加环境变量后重启(helm 等价于 --set pilot.env.PILOT_ENABLE_GATEWAY_API_COPY_LABELS_ANNOTATIONS=false)
PILOT_ENABLE_GATEWAY_API_COPY_LABELS_ANNOTATIONS=false

# 然后原样重跑:patch gateway label 1.30.2 → 1.30.3
```

- **中断消失** → 机制确定,就是这条复制链。再往下缩一环:
  - 看 LB 侧:`kubectl -n <ns> get svc <gw>-istio -w`,观察 EXTERNAL-IP / 端口是否瞬闪
  - 看有没有东西按 `istio.io/rev` 选 Pod:
    ```bash
    kubectl get networkpolicy,pdb -A -o json \
      | jq '.. | objects | select(.matchLabels?) | .matchLabels | select(has("istio.io/rev"))'
    ```
- **中断还在** → 这条链被证伪,做实验二。

### 4.2 决定性实验二:确认方式 B 里 gateway 有没有真的迁移过去

因为两种方式下 pod template 都该变,若方式 B 里 Deployment 根本没滚,那"无中断"只是"什么都没发生":

```bash
NS=<ns>; GW=<gateway-name>
kubectl -n "$NS" get deploy "$GW-istio" -o jsonpath=\
'{.metadata.generation}{"  "}{.spec.template.spec.containers[?(@.name=="istio-proxy")].image}{"\n"}{.spec.template.spec.containers[?(@.name=="istio-proxy")].env[?(@.name=="CA_ADDR")].value}{"\n"}'

istioctl proxy-status | grep "$GW"     # 最后一列应指向 istiod-1.30.3-xxx
```

如果 `CA_ADDR` / proxy-status 仍停在 `istiod-1.30.2`,则方式 B 的对比前提不成立,需要重做。

## 5. Tag 真正的好处

除了上面那条"扰动面更小",tag 还有几项纯运维层、但实打实的好处:

| 好处 | 说明 |
| --- | --- |
| **完全不动 Gateway 对象** | 翻 tag 只改 `MutatingWebhookConfiguration istio-revision-tag-<tag>` 与 `Service istiod-<tag>` 两个集群级对象;所有 Gateway / namespace / Deployment 的 label **一个字节都不变** —— 连带那 5 个生成对象的 metadata 也不动 |
| **一次翻转、原子生效** | `istioctl tag set canary --revision 1-30-3 --overwrite` 改的是**同名** webhook(update,不是 delete + create),所有标了 `canary` 的对象在同一瞬间一起切过去 |
| **回滚成本极低** | 把 tag 翻回去就回滚了。硬编码 revision 名要再全改一遍,还得记得原值 |
| **有一张显式映射表** | `istioctl tag list` 随时可查;revision 名本身没有任何登记处(虽然 `--set revision=X` 也会隐式建一个同名 tag) |

官方文档的措辞也正是这个角度:

> Revision tags are stable identifiers that point to revisions and can be used to avoid relabeling
> namespaces… Manually relabeling namespaces when moving them to a new revision can be
> **tedious and error-prone**.

## 6. 一个真实的语义差异:无人认领的中间态

tag 与 revision 名有一处**确实不同**的行为,值得记住。

如果你**先把 label 改成 `1-30-3`,但 1-30-3 的 istiod 还没装好或还没就绪**,那么所有 istiod 的
`IsMine` 全为 false:

- **带上 [Gateway 配置清空 Bug](Gateway配置清空Bug.md) 的修复之后**:旧 istiod 仍发配置所以流量不挂,
  但 **Deployment 没人管,新 Pod 永远起不来**,直到你装好为止
- **不修复的版本**:没有任何控制面发配置 → **立刻全挂**

tag 流程天然避开这个状态:先装好新 revision,再翻 tag(`istioctl tag set --revision X` 还会校验
revision 存在)。换句话说,**"改 label"这个动作把"声明"和"实现"耦合在了一次操作里,顺序很容易做错。**

## 7. 排查清单

```bash
# 1. 确认所有控制面版本(重点看 istiod,不是 client)
istioctl version

# 2. 确认待升级对象的 revision 名真实存在
istioctl tag list
kubectl get mutatingwebhookconfiguration -l istio.io/tag

# 3. 确认 route 上有没有 revision label(Gateway 配置清空 Bug 的残留那一半)
kubectl get httproute,grpcroute,tcproute,tlsroute -A -o json \
  | jq '.items[] | select(.metadata.labels["istio.io/rev"]) | .metadata'

# 4. 看副本数与滚动策略
kubectl -n <ns> get deploy <gw> -o jsonpath='{.spec.replicas}{"\n"}{.spec.strategy}{"\n"}'

# 5. 滚动期间盯 endpoints 会不会掉到 0
kubectl -n <ns> get endpoints <gw> -w
```

### 7.1 推荐的零停机升级流程

1. **装新 revision,并确认就绪。**
   `istioctl install --set revision=1-30-3`,等到 `istiod-1-30-3` 全部 Ready 再进入下一步。
2. **Gateway 的 `istio.io/rev` 只写 tag,永不写具体 revision 名。**
   例如固定写 `canary`,让这个值在整个生命周期内不变。
3. **翻 tag 完成切换。**
   `istioctl tag set canary --revision 1-30-3 --overwrite` —— 一次原子切换,Gateway CR 完全不动。
4. **HTTPRoute 不要打 `istio.io/rev`。** 这是目前唯一仍未修复的坑。
5. **保证 istiod 版本不低于 1.29.5 / 1.30.2 / 1.31.0。**
6. **给 gateway Deployment 足够的安全边际。**
   至少 2 副本 + PodDisruptionBudget + `strategy.rollingUpdate.maxUnavailable: 0`。
