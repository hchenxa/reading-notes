# 一字之差,两类代理:正向代理与反向代理详解

> 两个都叫"代理",一个站在客户端身边,一个站在服务器面前——方向不同,世界就完全不同。

## 01 从直连说起:为什么要有个"中间人"

互联网上最朴素的请求方式是**客户端直连服务器**:浏览器把请求发到服务器的 IP,服务器把响应原路返回。中间没有任何"转手"。

> 图1:无代理直连

```
[客户端] ──→ [目标服务器]
```

但真实世界里,直连常常行不通:目标服务器不让你直接访问、公司要求所有上网行为被记录、后端服务多到一台机器扛不住……于是"代理"(Proxy)登场了。

代理的本质是一个**代劳者**:它接收你的请求,代替你去联系目标,再把结果回传给你。就像点外卖时的骑手——你不需要走进餐厅,骑手替你完成取餐与配送。

引入代理的三大原始动机:

1. **身份隐藏**:服务器看不到真实请求者的身份与位置
2. **访问控制**:把流量收拢到一个统一入口做权限、内容管控
3. **性能加速**:代理层做缓存、压缩、连接复用,为两端减负

> 关键认知:代理本身不生产内容,它只负责"转发"。而根据它站在谁的身边,演进出了两大流派——正向代理与反向代理。

## 02 正向代理:站在客户端身边

### 定义

**正向代理(Forward Proxy)**部署在**客户端一侧**(通常是内网出口),代理的是**客户端**——它以客户端的名义,代替客户端向外发起请求。

> 图2:正向代理网络流向

```
[用户] ──→ [正向代理(Nginx)] ──→ [目标服务器]
```

### 请求流程

- STEP 01:客户端把请求发给正向代理,目标地址写在请求里(代理知道你要去哪)
- STEP 02:正向代理以**自己的身份**向目标服务器转发请求(服务器只看到代理的 IP)
- STEP 03:目标服务器把响应返回给代理
- STEP 04:代理把响应原样回传给客户端

### 核心特性

- **客户端知道目标是谁,目标不知道客户端是谁**:服务器看到的永远是代理的 IP
- 代理站在**请求方**一侧,客户端必须**主动配置**代理地址才会走它
- 典型部署位置:公司内网出口、个人电脑、抓包工具

### 典型场景

- **访问受限资源**:科学上网、内网穿透,绕开地理或网络限制
- **统一审计出口**:公司要求员工必须走公司代理上网,日志留存、内容过滤
- **缓存加速**:代理层缓存高频内容,内网重复请求不再出网
- **抓包调试**:Charles、Fiddler 的本质就是正向代理——手机把代理指向电脑,所有流量一览无余

### Nginx 正向代理配置演示

用 Nginx 搭一个最简单的正向代理,为内网客户端转发公网请求:

```nginx
# 正向代理:为内网客户端代理访问公网
server {
    listen       8080;               # 内网客户端把 HTTP 代理指向这里
    resolver     223.5.5.5;          # 由代理自己完成 DNS 解析
    server_name  _;

    location / {
        # 关键:动态转发到请求里携带的目标主机
        proxy_pass http://$http_host$request_uri;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

配置完成后,内网机器的 HTTP 代理设置为 `192.168.1.5:8080`,它的所有外网请求都会经过这台 Nginx 转发。

> 踩坑提示:nginx 做正向代理对 HTTPS 的 CONNECT 隧道支持并不完整,生产环境多为 Squid、Shadowsocks 等专业代理工具。这里拿 Nginx 演示,是为了让你用同一套工具看清"转发"的本质。

## 03 反向代理:站在服务器面前

### 定义

**反向代理(Reverse Proxy)**部署在**服务器一侧**(公网入口),代理的是**服务器**——它作为服务器的统一门面,替后端接受客户端的请求。

> 图3:反向代理网络流向

```
[用户] ──→ [反向代理(Nginx)] ──→ [后端服务器 A]
                                  [后端服务器 B]
                                  [后端服务器 C]
```

### 请求流程

- STEP 01:客户端以为自己在访问服务器,把请求发给反向代理(客户端只知道 Nginx 的域名)
- STEP 02:反向代理按规则选一台后端服务器,转发请求
- STEP 03:后端处理完,把响应返回给代理
- STEP 04:代理把响应回传给客户端

### 核心特性

- **客户端不知道后端是谁,后端也不知道客户端是谁**:双方都只认识 Nginx 这一个"中间人"
- 代理站在**服务方**一侧,客户端**无需任何配置**,它以为自己在直连服务器
- 天然支持多台后端:一台 Nginx 把流量按权重分发给服务器集群

### 典型场景

- **负载均衡**:一台 Nginx 分发到多台应用服务器,后端扩容只改配置
- **统一入口**:HTTPS 证书、域名解析、路由规则集中在一处,后端只管业务
- **安全防护**:隐藏后端真实 IP,集中做 WAF、限流、防攻击
- **动静分离**:静态资源 Nginx 直接返回,动态请求转发后端,减轻应用压力
- **微服务网关**:按路径把请求分发到不同服务,`/api/` 进订单服务,`/pay/` 进支付服务

### Nginx 反向代理配置演示

一个典型的反向代理 + 负载均衡配置:

```nginx
# 1) 定义后端服务器组(负载均衡池)
upstream backend_servers {
    server 192.168.1.10:8080 weight=3;   # 权重 3,承担更多流量
    server 192.168.1.11:8080 weight=1;
    server 192.168.1.12:8080 backup;     # 备份节点,前两台不可用时启用
}

# 2) 反向代理入口
server {
    listen       80;
    server_name  www.example.com;

    location /api/ {
        # 关键:把 /api/ 的请求转发给固定的后端服务器组
        proxy_pass http://backend_servers;

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

当客户端访问 `www.example.com/api/xxx` 时,Nginx 会根据权重选择一台后端处理,并把客户端的真实 IP 通过 `X-Forwarded-For` 头传给后端。

## 04 一张表看懂核心区别

| 维度 | 正向代理 | 反向代理 |
| --- | --- | --- |
| 部署位置 | 客户端一侧(内网出口) | 服务器一侧(公网入口) |
| 代表谁干活 | 代表**客户端**发请求 | 代表**服务器**接请求 |
| 服务器视角 | 只看到代理,看不到客户端 | 只能看到代理,看不到真正客户端 |
| 客户端视角 | 知道目标服务器,需要主动配置代理 | 以为代理就是服务器,零配置 |
| 后端真实 IP | 对客户端透明可见 | 被完全隐藏 |
| 典型用途 | 访问受限资源、审计、缓存、抓包 | 负载均衡、安全防护、统一入口 |

> 一句话亮点:正向代理是"代客户寻路",反向代理是"替服务器迎客"。

如果再简化一层,就记住**方向**:

- 正向代理 = **帮你访问别人**,客户端主动把代理"夹"进请求链路
- 反向代理 = **帮别人接待你**,服务器把代理"顶"在门前当门面

## 05 常见误区与选型建议

### 误区一:Nginx 就是反向代理

Nginx 两种代理都支持,正向代理的配置你上面已经见过了。只是生产环境里反向代理用得多,印象才被固化了。

### 误区二:走代理就等于加密

正向代理默认是**明文转发**的,它不做加密。想加密要靠代理本身支持 HTTPS CONNECT 隧道(或者 TLS),别把"走代理"和"安全"划等号。

### 误区三:有了反向代理就不需要正向代理

两者场景不同,完全可以**同时存在**:公司出口一个正向代理管审计,应用入口一个反向代理管负载,互不冲突。

### 误区四:反向代理隐藏了后端,后端就不用防护了

反向代理挡得住外部扫描,但挡不住**应用层攻击**(如 SSRF 利用代理访问内网)。后端该有的鉴权、校验、最小权限一个都不能少。

### 选型建议

- 想**访问别人**(出去)→ 正向代理
- 想**被别人访问**(进来)→ 反向代理
- 记忆锚点:正向代理是"代表你出门",反向代理是"代表家迎客"

## 写在最后

回顾全文,核心其实只有一句话:**代理都是那个"代劳者",区别只在于它替谁干活**。

替客户端干活,站在请求出发的一侧,是正向代理;替服务器干活,站在请求到达的一侧,是反向代理。下次再遇到陌生的代理概念,先问一句:"它站在哪边?"——方向对了,一切都顺了。
