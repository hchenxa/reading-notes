# 文档写作规范

> **类型**:Reference(规范)
> **状态**:已实测(2026-10-31)
> **版本基线**:仓库当前结构
> **适用**:本仓库所有 Markdown 笔记、README、实验记录
> **不覆盖**:代码风格、提交信息规范

这套规范解决三个问题:

1. 读者能在 30 秒内知道一篇文档**讲什么、是否可信、怎么用**;
2. 不同时间、不同主题写出来的文档**结构一致**;
3. "写文档"和"审文档"都有明确的检查项,不靠感觉。

配套文件:

| 文件 | 作用 |
|------|------|
| `docs/templates/` | 五种文档类型的骨架 |
| `.claude/skills/technical-docs/SKILL.md` | 写/改文档时执行的流程 |
| `.claude/agents/docs-editor.md` | 专职审稿 agent |
| `scripts/check_docs.py` | 机器能查的部分 |
| `CLAUDE.md` | 对以后所有会话的强制约束 |

---

## 一、先选文档类型

每篇文档只能有一个**主类型**。混合内容拆成多篇,或者用一种类型 + "本文不覆盖"链接到另一篇。

| 类型 | 回答的问题 | 读者状态 | 典型内容 |
|------|-----------|---------|---------|
| Explanation(解释) | 为什么、怎么理解 | 想建立心智模型 | 概念、架构、机制、取舍 |
| Tutorial(教程) | 跟着做能学会 | 第一次接触 | 从零到可运行,有固定结果 |
| How-to(操作指南) | 某个任务怎么做 | 已有基础,要解决具体问题 | 配置、迁移、排障步骤 |
| Reference(参考) | 字段/矩阵/默认值是什么 | 查资料 | 字段表、支持矩阵、约束 |
| Case study(排障记录) | 出了什么问题、根因是什么 | 遇到类似现象 | 时间线、根因、修复、验证 |

判断规则:

- 如果读者需要**按顺序做**,选 Tutorial;
- 如果读者带着一个**具体任务**来,选 How-to;
- 如果读者要**查一个值或字段**,选 Reference;
- 如果读者要**理解为什么**,选 Explanation;
- 如果文档围绕一次**事故/异常**,选 Case study。

文档类型写在元信息块里;骨架从 `docs/templates/` 对应文件复制。

---

## 二、元信息块(必填)

每篇文档标题下紧跟一个 blockquote 元信息块:

```markdown
> **类型**:How-to(任务导向)
> **状态**:已实测(2026-10-31)
> **版本基线**:Argo CD v3.5.6 / Dex v2.45.1
> **适用**:给 kind 上的 Argo CD 配 GitHub 登录
> **不覆盖**:LDAP、生产 Ingress TLS、RBAC 精细授权
```

### 状态词只允许四种

| 状态 | 含义 |
|------|------|
| `已实测(YYYY-MM-DD)` | 命令、输出、结论都在当前版本实际跑过 |
| `部分实测(YYYY-MM-DD)` | 只跑了一部分,必须写清哪些已验证、哪些没有 |
| `未实测(YYYY-MM-DD)` | 基于源码/官方文档整理,没有在当前环境跑过 |
| `设计稿(YYYY-MM-DD)` | 方案或计划,尚未验证 |

不要再使用"路线""已整理""进行中""待补充"这类模糊状态。

### 其他字段

- `版本基线`:文档针对的软件版本;行为随版本变化时必须写。
- `适用`:一句话说明读者和场景。
- `不覆盖`:明确边界,避免读者误以为这篇能解决所有相关问题。
- 日期只写在元信息块里,不要散落在正文。

## 三、通用骨架

所有类型共享以下顺序:

```markdown
# 标题

> 元信息块

## 一、结论先行
3-5 条,10 行以内。读者只读这一节也能知道结论。

## 二、正文
按类型骨架展开,见第四节。

## 验收 / 排错 / 边界与取舍
按类型选择,不是每篇都必须全有。

## 下一步
- [相关文档](...)

## 参考
- [外部链接](...)
```

硬性要求:

- **结论先行**:第一节必须是结论/速查/目标,不能是"背景"或"历史"。
- **一节一个主题**:H2 不写"其他""杂项"这类垃圾桶标题。
- **每篇结尾**:`## 下一步` 和 `## 参考` 至少有一个,推荐两个都有。
- **不复制**:同一主题只在 canonical 文档里展开,其他文档只链接。

## 四、五种类型的正文骨架

模板在 `docs/templates/`:

| 类型 | 模板 | 正文骨架 |
|------|------|---------|
| Explanation | [explanation.md](templates/explanation.md) | 一句话结论 → 心智模型 → 机制/时序 → 边界与取舍 → 常见误解 |
| Tutorial | [tutorial.md](templates/tutorial.md) | 你将完成什么 → 前置条件 → 步骤 → 验证 → 清理 → 常见问题 |
| How-to | [how-to.md](templates/how-to.md) | 目标与场景 → 前置条件 → 操作步骤 → 验证 → 回滚 → 排错 |
| Reference | [reference.md](templates/reference.md) | 速查表 → 字段与默认值 → 约束 → 示例 → 常见错误 |
| Case study | [case-study.md](templates/case-study.md) | 现象 → 影响面 → 时间线 → 根因 → 修复与验证 → 经验 |

## 五、写作规则

### 5.1 文件与目录

- 主题目录下的正文用 `NN-Title.md`,编号连续;README 作为主题入口。
- 实验清单放 `labs/` 子目录,不要和正文混在一起。
- 新增文档后更新该主题的 `README.md` 文件索引。
- **不要手改 `_sidebar.md`**,它由 `generate-sidebar.sh` 在构建时生成。
- 一个主题只有一个 canonical 文档;新文档如果和已有内容重叠,先合并或明确链接关系。

### 5.2 标题

- 全文只有 1 个 H1。
- H2 用中文序号:`## 一、标题`。
- H3 用 `### 1.1 标题`;不要出现 H4。
- 标题里不要用句号;不要写"首先/其次/最后"。
- 标题要能单独表达信息,不要写"其他""说明""补充"。

### 5.3 段落与列表

- 一段只讲一个观点,建议 2-5 句。
- 列表最多两层;超过两层说明结构需要拆。
- 不要用大段加粗;加粗只用于关键词和警告。
- 中文正文用中文标点;英文术语、命令、字段用反引号。

### 5.4 代码块

- 必须带语言标记:`bash`、`yaml`、`json`、`text`、`mermaid` 等。
- 命令用 `bash`,不带 `$`,方便复制。
- 输出单独用 `text` 块;不要把命令和输出混在一个块里。
- 占位符用 `<...>` 或 `REPLACE_...`;不要出现真实密码、token、私钥。
- 长 YAML 只保留和本节相关的字段,完整清单放到 `labs/` 或附录。

### 5.5 表格

- 只放结构化数据;长段落不要塞进单元格。
- 列数控制在 5 列以内;超过就拆表。
- 表头必须有意义,不要用"字段1/字段2"。
- 表格前后各留一个空行。

### 5.6 提示块

统一用 blockquote + 粗体标签:

```markdown
> **注意**:...
> **坑**:...
> **未实测**:...
> **安全**:...
```

不要用 GitHub 的 `[!NOTE]` / `[!WARNING]`,docsify 对它的支持不稳定。
每节最多一个提示块;提示太多等于没有提示。

### 5.7 链接与引用

- 仓库内文档用相对链接;外部资源用完整 URL。
- 链接文字要描述目标,不要写"点这里"。
- 每篇结尾的 `## 参考` 只放外部资料;内部下一篇放 `## 下一步`。
- 引用外部结论时,在链接旁写版本或日期。

### 5.8 事实、状态与版本

- **没跑过的命令,不要写"输出如下"**;写"预期输出"并标 `未实测`。
- 状态必须和实际执行情况一致;部分验证就写 `部分实测`。
- 版本相关行为写进元信息块或在正文标注版本。
- 不编造命令输出、日志、错误码;需要示例时明确写"示例"。

### 5.9 术语与语气

- 术语首次出现写全称 + 缩写,例如"配置管理插件(Config Management Plugin,CMP)"。
- 同一概念只用一个中文名;英文 API 对象名保留原文。
- 用陈述句,不用"我们认为""大家都知道"。
- 不确定的地方直接写"不确定"或"未验证",不要用模糊措辞掩盖。

### 5.10 安全

- 文档中不出现真实凭据、token、私钥、内网地址(除非是实验占位)。
- Secret 只写引用方式或占位符。
- 涉及删除、覆盖、破坏性操作时,用 `> **安全**:` 明确警告并给回滚方法。

## 六、审稿清单

写完或改完一篇文档,逐项检查:

- [ ] 类型明确,元信息块完整(类型/状态/版本/适用/不覆盖)
- [ ] 全文 1 个 H1;H2 中文编号;H3 为 `1.1`;没有 H4
- [ ] 第一节是结论/速查/目标,不是背景
- [ ] 有前置条件(如果是操作类)
- [ ] 每个命令有语言标记;命令和输出分开
- [ ] 有验证步骤或验收清单
- [ ] 有排错表(如果是操作类)
- [ ] 边界/不覆盖写清楚
- [ ] 有 `## 下一步` 或 `## 参考`
- [ ] 没有重复展开其他 canonical 文档的内容
- [ ] 主题 README 索引已更新
- [ ] 没有真实 secret
- [ ] `python3 scripts/check_docs.py <文件>` 无 error

## 七、自动化检查

```bash
# 检查指定文件
python3 scripts/check_docs.py ArgoCD/07-SSO与Dex.md

# 检查全仓库(输出 warning,不阻塞)
python3 scripts/check_docs.py

# CI 模式:warning 也当 error
python3 scripts/check_docs.py --strict
```

检查内容:

- 代码块是否闭合、是否有语言标记
- H1 数量、标题层级是否跳级
- 表格列数是否一致
- 相对链接目标是否存在
- 元信息块是否存在、状态词是否合法
- 类型对应的必需章节是否存在(warning)

新文档要求零 error、零 warning;存量文档逐步修,不要求一次全部通过。

---

## 八、迁移策略

1. **新文档立即执行**本规范。
2. 存量文档按优先级重构:**07 → 06 → 03 → 04 → 00 → 其余**。
3. 结构重排和技术内容修改**分两次提交**,避免审阅时混淆。
4. 重构时保留所有已实测输出;只调整结构和措辞,不重写事实。
5. 每重构完一篇,在 `README.md` 状态列更新为 `已整理` 或 `已实测`,并跑一次检查脚本。
