PART


单向信任：浏览器时代的设计

ONE-WAY TRUST

为什么平时“只有服务器出示证书”

你天天访问 HTTPS 网站，都是服务器出示证书、浏览器验证——为什么客户端不用证明自己？因为浏览器时代的设计假设是：

1

服务器是稀缺的、固定的：全世界就一个 example.com，它必须证明“我是 example.com”

2

客户端是海量的、匿名的：任何浏览器用户都允许访问公开网页，不需要（也不应该）暴露身份

3

信任锚是系统预置的：浏览器内置几百个受信根 CA，验证服务器的链

这套设计服务于“任何人访问公开网站”，非常成功——但它默认了一个前提：服务器需要被验证，客户端不需要。

这个模型在服务间对话时失灵

当对话双方变成“服务 A ↔ 服务 B”，单向信任的漏洞立刻显现：

1

服务 A 作为客户端访问 B 时，它验证了 B 的证书——但 B 无法验证调用它的是不是真的 A

2

谁都能调用你的内部 API：只要证书合法（或直接在内网），服务 B 无法区分“真 A”和“伪装成 A 的攻击者”

3

审计需求：出了事故，你无法证明“哪个服务在什么时间调用了什么”

关键认知：单向 TLS 验证的是“连接的另一端有合法证书”，而任何一端都能拿到一张合法证书——它证明不了“调用者是谁”。mTLS 补上的正是这一环：让连接的两端互相证明身份。

02

PART


mTLS 握手：多了哪两步

HANDSHAKE DELTA

握手差异对比

对比单向 TLS 1.2 握手，mTLS 只是多了两个环节——但方向完全反转：

STEP 01

ClientHello（与单向一致）

客户端发 ClientHello，带 SNI 和密套列表。

STEP 02

服务器加发 CertificateRequest

服务器发 ServerHello + 证书链，额外发一个 CertificateRequest——“请你也出示证书”。

✓

双向验证服务器证书（与单向一致）

客户端验证服务器证书链。

NEW

客户端出示自己的证书

客户端发 Certificate 消息，出示自己的证书链。

NEW

CertificateVerify：用私钥签名

客户端用私钥对握手摘要签名，服务器验证签名——证明“持证人在场”。

STEP 05

密钥交换，开始加密通信

双方完成密钥交换，进入业务数据阶段。

✦ 灵魂一步

CertificateVerify 是 mTLS 的灵魂——证书本身是公开的、可以伪造，但签名必须用私钥。服务器验证签名后，才能确定“持证人在场”。这是“证明我是我”的密码学落地。

验证路径：从单向到双向

单向 TLS：客户端 ——验证——>； 服务器证书 ——链到——>； 客户端信任的根 CA

mTLS：客户端 ——验证——>； 服务器证书 ——链到——>； 客户端信任的根 CA

　　　　服务器 ——验证——>； 客户端证书 ——链到——>； 服务器信任的根 CA

注意一个细节：双方可以信任不同的 CA——内部服务信任公司内部 CA 签发的客户端证书，同时仍信任公共 CA 签发的服务器证书，两端各有各的信任锚。

03

PART


为什么服务间需要 mTLS

WHY MTLS

三个真实场景

1

B2B / 内部 API：支付网关、用户中心这类敏感服务，只接受持有合法客户端证书的调用方——比 API Key 更安全，私钥不随代码走，无法被日志泄露

2

微服务集群：服务间调用频繁，用户名密码/Token 的接入与审计成本高——证书即身份

3

物联网 / 设备认证：设备出厂预置证书，平台用 mTLS 区分“这台设备”和“仿冒设备”

mTLS 与 API Key 的对比

维度 API Key mTLS
泄露风险 明文头，日志/截图/前端都可能泄露 私钥不出设备
冒充难度 偷到 Key 即可冒充 需要私钥
轮换成本 改配置 换证书（可短生命周期）
审计 无标准 证书 CN/SAN 可审计

API Key 是“进门报口令”，mTLS 是“进门刷身份证还按指纹”——口令能抄，指纹不能

动手：nginx 双向认证从零跑通

HANDS-ON

这一节完整搭一套：内部 CA → 服务端证书 → 客户端证书 → nginx 双向校验 → curl 验证“不带证书被拒、带证书放行”。

STEP 01

创建内部 CA

. . . bash

# 1. 生成 CA 私钥

openssl genrsa -out ca.key 2048

# 2. 自签 CA 根证书(有效期 10 年)

openssl req -x509 -new -key ca.key -days 3650 \

　 -subj "/CN=Internal Root CA" -out ca.crt

STEP 02

签发服务端证书（带 SAN）

. . . bash

# 1. 服务端密钥对 + CSR

openssl genrsa -out server.key 2048

openssl req -new -key server.key \

　 -subj "/CN=example.com" -out server.csr

# 2. CA 签名,必须带 SAN(现代客户端只看 SAN)

openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key \

　 -CAcreateserial -days 365 -out server.crt \

　 -extfile <(echo "subjectAltName=DNS:example.com,DNS:localhost,IP:127.0.0.1")

STEP 03

签发客户端证书

关键点：客户端身份写在 CN 里——证书即身份：

. . . bash

openssl genrsa -out client.key 2048

openssl req -new -key client.key \

　 -subj "/CN=client-01/OU=payment-service" -out client.csr

openssl x509 -req -in client.csr -CA ca.crt -CAkey ca.key \

　 -CAcreateserial -days 365 -out client.crt

STEP 04

nginx 开启双向认证

. . . nginx

server {

　　listen　　　 8443 ssl;

　　server_name　example.com;

　　ssl_certificate　　 /etc/nginx/certs/server.crt;

　　ssl_certificate_key /etc/nginx/certs/server.key;

　　# ===== mTLS 核心:客户端证书校验 =====

　　ssl_client_certificate /etc/nginx/certs/ca.crt;　# 信任的 CA

　　ssl_verify_client　　　on;　 # 强制校验:拿不出证书直接拒

　　ssl_verify_depth　　　 2;　 # 允许的证书链深度

　　location / {

　　　　# 把客户端身份透传给后端应用

　　　　proxy_set_header X-Client-CN　　 $ssl_client_s_dn;

　　　　proxy_set_header X-Client-Verify $ssl_client_verify;

　　　　proxy_pass http://127.0.0.1:8080;

　　}

}

STEP 05

验证双向认证生效

. . . bash

# 1. 不带客户端证书 → 握手被拒

curl -k https://127.0.0.1:8443/

# HTTP/2 400 ... client certificate required ← 服务器:请出示证件

# 2. 带客户端证书 → 放行

curl -k --cert client.crt --key client.key https://127.0.0.1:8443/

# 200 OK

# 3. 带"别人 CA 签的"证书 → 还是被拒(信任链断裂)

curl -k --cert other-ca.crt --key other.key https://127.0.0.1:8443/

# 400 ... failed to verify client certificate

！踩坑提示 🕳

nginx 校验的是“证书链能否追溯到 ssl_client_certificate 里的 CA”，不是“证书没过期”那么简单——签发客户端证书的 CA 必须与服务器配置的 CA 一致，否则必然 400。

STEP 06

服务器如何知道“谁在敲门”

nginx 暴露了三个变量，后端应用靠它们做授权：

. . . nginx 变量

$ssl_client_verify　 # SUCCESS / FAILED / NONE

$ssl_client_s_dn　　 # 客户端证书 Subject,如 /CN=client-01/OU=payment-service

$ssl_client_i_dn　　 # 签发该证书的 CA

后端拿到 X-Client-CN，按 CN 前缀做授权（如 payment-service 才能调支付接口）——这就是“证书即身份”的应用层落地。

PART


内部 PKI：为 mTLS 造一个信任锚

INTERNAL PKI

mTLS 的强度不取决于 TLS 本身，而取决于你信任的 CA 有多可靠：

根 CA（离线保管，几乎不签叶子）

　└── 中间 CA A（服务器证书签发）

　└── 中间 CA B（客户端证书签发）　← 按用途拆分，吊销/轮换互不影响

拆分的三个理由：

1

隔离风险：一个中间 CA 私钥泄露，只吊销它的证书，根 CA 不用动

2

职责分离：签发服务器证书和客户端证书可以走不同的审批流程

3

短期证书成为可能：中间 CA 只签 24h/7d 的证书——证书越短，吊销需求越小，轮换自动化越简单

证书轮换的哲学：短命证书是解药

单向 TLS 的证书可以一年一换，吊销体系（CRL/OCSP）能兜底。但 mTLS 的客户端证书有个现实困境：被吊销的证书，在 CRL 更新前还能用（吊销滞后）。于是行业共识变成：

与其设计完美的吊销，不如让证书短命——24 小时一签，泄露了也只用防一天

架构实践：网格、网关与零信任

ARCHITECTURE

微服务网格：Sidecar 之间的 mTLS

Pod A

Sidecar

—mTLS→

Pod B

Sidecar

Istio 这类网格把 mTLS 变成默认：每个 Pod 的 Sidecar 持有短期证书，服务代码完全无感知；STRICT 模式下明文流量直接拒绝——横向移动被阻断：攻破 Pod A，想访问 Pod B 必须过 B 的 Sidecar 这关，而 A 的证书只授权给 A 的身份。

API 网关与 B2B：同端口双模式

网关对外可以同时面向两类调用方：浏览器走普通 TLS，合作方/内部系统走 mTLS。nginx 用 ssl_verify_client optional 实现“同端口双模式”：

. . . nginx

ssl_client_certificate /etc/nginx/certs/ca.crt;

ssl_verify_client　　　optional;　 # 有证书就校验,没有也放行到应用层

# 应用层按 $ssl_client_verify 分流:SUCCESS → B2B 逻辑;NONE → 公开逻辑

零信任里的位置

零信任的核心假设是“内网不等于可信”。mTLS 是零信任的传输层基石：每次调用都要证明身份，不因为“我们在同一个内网”就放行。但记住：mTLS 只解决“谁在调用”，调用权限要由授权策略（SPIFFE 联邦、RBAC）继续管。

07

PART


运维与坑

PITFALLS

坑一：证书轮换断了线上

客户端证书到期后，所有调用方一起 400——mTLS 的轮换必须两端协调：先给所有调用方发新证书并灰度切换，再等旧证书自然过期，不能一刀切。

坑二：忘记 SAN

服务端证书没有 SAN，现代客户端直接拒绝——生成时的 -extfile 那行不能省。

坑三：吊销滞后

CRL 更新周期内，被盗客户端证书依然有效。缓解：短生命周期证书 + 及时上报 + 吊销列表高频更新。

坑四：把客户端私钥塞进代码仓库

客户端证书是身份凭证，私钥泄露等于身份泄露——必须走密钥管理（KMS/HSM）或加密存储，绝不能进 git、不能进镜像层、不能进日志。

坑五：双向验证开了，后端没接身份

nginx 校验了证书，但后端不读 $ssl_client_s_dn 做授权——那 mTLS 就只是个“昂贵的连接加密”。身份要一直传到应用层才有意义。

坑六：测试环境也用“真 CA”

测试证书应由测试用的独立 CA 签发，和生产的 CA 严格分开——防止测试证书在生产被意外信任。

✦ 排障三板斧

curl -vk 看握手失败在哪一步；openssl verify -CAfile ca.crt client.crt 验证证书链；nginx 日志里看 $ssl_client_verify 是 SUCCESS 还是 FAILED。

08

PART


与身份体系的配合

IDENTITY

mTLS ≠ 用户身份

mTLS 证明的是“这台设备/这个服务持有一张由可信 CA 签发的证书”，不等于“这个人类用户是谁”。Web 场景里用户身份仍靠 OIDC/SSO，设备身份才靠 mTLS——两者是叠加关系，不是替代关系。

SPIFFE：服务身份的事实标准

SPIFFE 定义了服务身份的标准格式：

. . . SPIFFE ID

spiffe://trust-domain/ns/namespace/sa/service-account

　　　　　└─ 信任域 ─┘　 └──────── 路径 = 身份声明 ────────┘

X.509-SVID 是它的证书载体——证书里的 SAN 直接编码 SPIFFE ID。Istio、Consul 都遵循它。设计启示：证书的 CN/SAN 不只是名字，是机器可读的身份声明，值得认真设计你的命名规范。

WRAP UP

mTLS 的完整故事是一条线：

单向 TLS 验证“服务器是真的”→ 服务间场景需要“调用者是真的”→ 握手多出两步 → 证书变成身份凭证 → 身份凭证需要自己的 PKI → PKI 需要短命证书与自动化 → 网格把这一切变成默认。

记住三个判断句：mTLS 解决“谁在敲门”，不解决“能敲哪扇门”；客户端私钥 = 身份本身，泄露等同沦陷；证书越短命，mTLS 越好运维。
