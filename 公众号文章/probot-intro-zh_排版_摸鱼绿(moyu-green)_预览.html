Probot 是什么？

WHAT IS PROBOT

Probot 是一个用 Node.js 构建 GitHub App 的框架。它的核心理念：GitHub 上的事件驱动你的代码。

当你安装一个 GitHub App 到仓库或组织后，GitHub 会把所有你订阅的事件以 webhook 的形式推送到你的服务器。Probot 负责处理这条链路里所有枯燥的工程问题：


签名校验

接收并校验 webhook 签名（HMAC，确保请求真的来自 GitHub）


认证与令牌

用 App 私钥签发 JWT、换取安装令牌，并以 App 身份调用 GitHub API


事件封装

把原始 JSON payload 封装成好用的 context 对象交给你的处理函数


内置服务器

内置一个 HTTP 服务器，并自带日志、健康检查、静态页面

你只需要写一件事：「当事件 X 发生时，做什么」。整个框架的核心 API 也就一句话：app.on(event, handler)。

PART


工作原理

HOW IT WORKS

GitHub 推送 webhook

事件到达，Probot 校验签名

→

app.on 事件路由

订阅的事件进入对应 handler

→

context.octokit 写回

自动认证，调用 GitHub API

入口：module.exports = (app) => { … } · 动作：context.octokit 读写 GitHub

入口：module.exports = (app) => { … }，你的 App 就是一个接收 Probot 实例的函数

事件：app.on() 订阅 GitHub webhook 事件

动作：handler 里用 context.octokit 调用 GitHub API，写回状态

快速开始

QUICK START

STEP 01

注册一个 GitHub App

到 github.com/settings/apps/new 注册一个 App：


Webhook URL

指向你的服务器（如 https://your-host/api/github/webhooks）


Webhook secret

任意随机字符串，用于签名校验


Permissions

按需勾选（issues: write、pull_requests: write、checks: write 等）


Subscribe to events

勾选你要处理的事件

注册完成后生成私钥（.pem 文件），记下 App ID 和 secret。

！踩坑提示 🕳

改 app.yml ≠ 订阅事件。最终生效的是 GitHub App 设置页：改完必须同步去设置页勾选事件与权限，否则事件永远不会投递（san-ci 为 workflow_run 踩过这个坑）。

STEP 02

创建项目

bash

npx create-probot-app　　# 官方脚手架，交互式生成项目

或者手动搭：

bash

npm install probot

mkdir src && touch src/index.js

最小 App：

. . . js

module.exports = (app) => {

　　app.log.info('Bot started')

　　app.on('issues.opened', async (context) => {

　　　　const issue = context.payload.issue

　　　　await context.octokit.rest.issues.createComment({

　　　　　　...context.repo(),

　　　　　　issue_number: issue.number,

　　　　　　body: 'Thanks for opening this issue!'

　　　　})

　　})

}

启动：

bash

npx probot run ./src/index.js

STEP 03

配置环境变量并运行

bash

export APP_ID=12345

export PRIVATE_KEY_PATH=/path/to/your-app-key.pem

export WEBHOOK_SECRET=your-secret

npx probot run ./src/index.js

v14 默认监听 3000 端口，webhook 路径为 /api/github/webhooks。也可以都用环境变量（见文末速查表）。

✦ 首次运行免配置

第一次运行没有凭据时，probot run 会进入 setup 模式：自动帮你注册 App、生成私钥、写入 .env，并把 webhook 指向一个 smee.io 代理（本地开发用）——开箱即用。

核心 API 详解

CORE API

Probot 实例（app）

你的模块收到一个 Probot 类实例。v14 的方法如下：

方法 / 属性 说明
app.on(event, handler) 订阅事件。event 可以是字符串、字符串数组，支持通配符（'pull_request.*' 匹配该事件所有 action，'*' 匹配所有事件）
app.onAny(handler) 订阅所有事件，常用于打日志、统计
app.onError(handler) 订阅处理异常，统一错误处理
app.load(appFn) 加载另一个 App 函数（支持数组），可组合多个 bot
app.receive({ name, payload }) 手动投递一个事件（测试用，不起服务器）
app.auth(installationId) 返回某个安装的认证客户端，主动发 API（不在 webhook 上下文里时用）
app.webhooks 底层 webhook 处理器（@octokit/webhooks 实例）
app.log 全局日志器
app.ready() 等待初始化完成
app.getNodeMiddleware() 把 webhook 处理转成标准 Node 中间件，可挂到任意 HTTP 服务器
app.version Probot 版本号
. . . js

// 同一个 handler 处理多个事件

app.on(['pull_request.opened', 'pull_request.synchronize'], async (context) => {

　　// 新开 PR 和推新提交都重新评估 CI 门禁

　　await handleRebaseAndGate(context, context.payload.pull_request)

})

// 通配符：订阅 pull_request 的所有 action

app.on('pull_request.*', async (context) => { /* ... */ })

// 统一错误处理

app.onError(async (error) => {

　　app.log.error({ err: error }, 'Webhook handler failed')

})

Context（context）

每个 handler 收到一个 Context 实例，它把你需要的几乎一切都打包好了：

成员 说明
context.payload GitHub 发来的原始 webhook JSON（payload.pull_request、payload.comment、payload.review…）
context.octokit 已认证的 Octokit 客户端（按当前安装自动换令牌，并自动带 x-github-delivery 请求头便于排查）
context.log 带事件上下文的子日志器
context.name 事件名（如 pull_request）
context.id webhook delivery ID
context.isBot 只读属性，事件操作者是否是 bot
context.repo(obj?) 返回 { owner, repo }，可合并参数
context.issue(obj?) 返回 { owner, repo, issue_number }
context.pullRequest(obj?) 返回 { owner, repo, pull_number }
context.config(file, default?) 读取仓库 .github/<file> 的 YAML 配置（见下）

参数构造器是写起来最顺手的 API，直接喂给 REST 调用：

. . . js

app.on('issues.opened', async (context) => {

　　const params = context.issue({ body: 'Hello!' })

　　// => { owner: 'octocat', repo: 'hello-world', issue_number: 1347, body: 'Hello!' }

　　await context.octokit.rest.issues.createComment(params)

})

context.config() 让用户可以用仓库里的 YAML 文件配置你的 bot（只从默认分支读取，安全）：

. . . yaml

# .github/config.yml（用户仓库）

close: true

comment: Check the specs on the rotary girder.

. . . js

// 没有配置文件时用默认值

const config = await context.config('config.yml', { close: false })

if (config.close) {

　　await context.octokit.rest.issues.update(context.issue({ state: 'closed' }))

}

context.octokit —— 完整的 GitHub REST API

context.octokit 是 @octokit/rest 的完整实例，几百个端点全覆盖：context.octokit.rest.issues.*、pulls.*、checks.*、repos.*……另外还内置：

. . . js

// 遍历组织下所有 open PR

const openPrs = await context.octokit.paginate(

　　context.octokit.rest.pulls.list,

　　{ owner, repo, state: 'open', per_page: 100 }

)

另外还内置分页遍历：context.octokit.paginate() 自动翻页、遍历所有结果；同时支持可插拔插件体系，比如 octokit-plugin-config（context.config 的底层）、octokit-plugin-create-pull-request 等。

Probot 构造函数

不经过 CLI 也可以直接编程使用，测试和嵌入场景很常用：

. . . js

const { Probot } = require('probot')

const probot = new Probot({

　　appId: 12345,

　　privateKey: '-----BEGIN RSA PRIVATE KEY-----...',

　　secret: 'webhook-secret',

　　githubToken: 'ghp_...',　// 测试模式：用个人令牌代替 App 认证

　　// Octokit: MyCustomOctokit,　// 自定义 Octokit 类（加插件）

　　// baseUrl: 'https://ghe.example.com/api/v3',　// GitHub Enterprise

})

probot.load(appFn)　// 加载你的 App

probot.receive({ name: 'pull_request', payload })　// 投递事件

注意构造时 githubToken 和 appId/privateKey二选一——测试环境用前者，生产用后者。

事件参考

EVENTS

GitHub 有几十种 webhook 事件，常见的有：

事件 触发时机 典型用途
issues.opened Issue 生命周期 问候、模板检查
pull_request.opened PR 生命周期 门禁检查、lint、DCO
pull_request.labeled 标签变化 状态机驱动
pull_request_review.submitted 评审提交 批准逻辑
issue_comment.created 评论创建 slash 命令入口
check_run.completed Check Run 结束 外部 CI 完成后重新评估
workflow_run.completed GitHub Actions 工作流结束 同上（Actions 场景）
status 旧式 commit status 更新 兼容旧 CI
push 推代码 触发构建、自动 rebase
repository_dispatch 外部手动触发 定时任务入口（配合 cron workflow）
installation.created App 被安装/卸载 初始化/清理
schedule 定时（Probot 内置） 周期任务

san-ci 用 repository_dispatch + cron workflow 实现每天一次的 stale 检查——App 本身不需要常驻定时器。

实战模式：用这些 API 能搭出什么

PATTERNS

模式一：slash 命令

issue_comment.created 是所有 slash 命令（/lgtm、/approve、/rebase…）的入口。解析评论 → 查权限 → 执行动作：

. . . js

app.on('issue_comment.created', async (context) => {

　　const comment = context.payload.comment

　　const issue = context.payload.issue

　　if (!issue.pull_request) return　// 只在 PR 上生效

　　const cmd = comment.body.trim().split(/\s+/)[0].replace(/^\//, '')

　　switch (cmd) {

　　　　case 'lgtm':

　　　　　　// 打标签 + 提交 APPROVED review

　　　　　　break

　　　　case 'assign':

　　　　　　// 添加 assignee

　　　　　　break

　　}

})

san-ci 的分发器在 src/commands.js，权限模型挂在仓库的 OWNERS 文件上（approvers/reviewers 名单），/lgtm 只有 approver 能用。

模式二：标签即状态机

不用数据库，PR 状态用标签表达（lgtm、approved、needs-rebase、do-not-merge/hold…）。每次事件到达就全量重算状态并同步标签——无状态、幂等、不怕丢事件：

. . . js

app.on('pull_request.labeled', async (context) => {

　　const pr = context.payload.pull_request

　　if (context.payload.label.name === 'lgtm') {

　　　　await context.octokit.rest.issues.addLabels(context.issue({ labels: ['approved'] }))

　　}

})

模式三：Check Run 作为状态 UI

用 checks: write 权限创建 Check Run，把 bot 的状态展示在 PR 的 checks 列表里，还能作为 branch protection 的 required check：

. . . js

await context.octokit.rest.checks.create({

　　...context.repo(),

　　name: 'Review Gate',

　　head_sha: pr.head.sha,

　　status: 'queued',

　　output: { title: '⏳ Needs review', summary: '...' }

})

san-ci 的门禁就是这样一个叫 Review Gate 的 check：⏳ Needs review → ✅ All checks passed → 自动 squash-merge。

模式四：定时任务

方案 A：GitHub Actions cron workflow 发 repository_dispatch，App 收到后执行（san-ci 的做法，推荐——GitHub 替你扛调度）。

方案 B：App 自己用 setInterval/schedule 事件（仅当 App 常驻且只有一个实例时可靠）。

本地开发与测试

DEV & TEST

用 fixture 模拟事件（不需要真实 GitHub）

CMD npx probot receive -e pull_request -p ./test/fixtures/pull_request.opened.json ./src/index.js

v14 的 CLI 是 receive（v12 时代叫 simulate）。fixture 就是一条抓下来的真实 webhook payload，开发时从 GitHub 抓一条存进仓库，以后反复用。san-ci 的 fixture 在 test/fixtures/ 下。

本地联调真实 webhook

probot run 内置 smee.io 代理支持：-W, --webhook-proxy <url>。本地起一个 smee 通道，把 URL 填到 GitHub App 设置页的 Webhook URL，真实事件就能流到你的本地进程——首次 setup 模式会自动配好这一切。

单元测试：nock + probot.receive()

Probot App 本质是“事件进、API 调用出”，测试时 mock 掉所有 GitHub API 即可。san-ci 用 Node 内置 node:test + nock：

. . . js

const { Probot } = require('probot')

nock.disableNetConnect()

test('opened PR triggers reviewer suggestion', async () => {

　　const probot = new Probot({ githubToken: 'test-token' })

　　await probot.load(appFn)

　　// mock 顺序必须与代码调用顺序一致

　　nock('https://api.github.com').get('/repos/octocat/hello/contents/OWNERS').reply(200, ...)

　　nock('https://api.github.com').post('/repos/octocat/hello/issues/1/comments').reply(201, ...)

　　await probot.receive({

　　　　name: 'pull_request',

　　　　payload: fixture.pullRequestOpened

　　})

})

afterEach(() => nock.cleanAll())

✦ 测试模式小技巧

Probot 构造函数传 githubToken 会跳过 App 认证，直接以该令牌调用 API，测试里就不用准备私钥了。

配置 CLI 环境变量 默认值

私钥 -P, --private-key <file> PRIVATE_KEY_PATH 或 PRIVATE_KEY —

部署

DEPLOYMENT

Probot App 就是一个 HTTP 服务，部署 = 跑一个 Node 进程。最简单的形态：

bash

npm install --production

APP_ID=... PRIVATE_KEY_PATH=... WEBHOOK_SECRET=... npm start

可以部署在任何能跑 Node 的地方：VM、K8s、Azure Functions、Vercel、Glitch。或者用 app.getNodeMiddleware() 把 webhook 处理挂进你现有的 Express/Node 服务。

两个生产注意点：

1

至少两个实例：webhook 没有“至少一次投递”保证，丢失要能自愈——把 handler 写成幂等的（“全量重算”模型天然满足）

2

高吞吐场景：配 REDIS_URL 启用请求限流的集群支持，避免触发 GitHub 的 rate limit

常见坑（webhook 开发的通用经验）

PITFALLS

1

review 的 body 不会触发 issue_comment.created。reviewer 在评审里写 /lgtm，到达的只有 pull_request_review.submitted。所以要在该 handler 里把“长得像命令”的 review body 手动重构成 comment 再分发——san-ci 用 Object.create(context) 而不是对象展开，因为展开会丢掉 context 原型上的 repo() 等方法。

2

listPullRequestsAssociatedWithCommit 可能返回空数组。用 commit SHA 反查 PR 时不要相信空结果（san-ci 在 genai-io/san#459 实际遇到过），要退回全量扫描 open PR 匹配 head.sha。workflow_run 事件则直接带 pull_requests 数组，不用查。

3

webhook payload 是“事件发生那一刻”的快照。你的 handler 自己刚打的标签、刚合的 PR，在 payload 里看不到——需要时重新 pulls.get 拉最新状态。

4

改 app.yml ≠ 订阅事件。生效的是 GitHub App 设置页。

小结

Probot 把 GitHub App 开发里90% 的重复工程（认证、令牌、webhook 服务器、签名校验）压缩成了几行配置，留给你的是纯粹的业务逻辑。

核心心智模型只有一个：事件进，context.octokit 出——app.on() 订阅，handler 里写逻辑，用 context.issue()/context.repo() 构造参数，用 context.octokit 读写 GitHub。

掌握这一个循环，再加上标签状态机、Check Run、slash 命令这几个组合拳，你就能搭出 san-ci 那样的组织级自动化。
