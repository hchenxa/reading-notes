一句口诀收尾

同样叫“代理”，方向却完全相反

一个站在客户端身边，一个站在服务器面前

两个都叫“代理”，却常常被混为一谈。这篇不讲虚的：先看清两种代理的定义与网络流向，再用 Nginx 把配置一步步演给你看，最后一张表收掉全部区别。

建议收藏这篇——面试被问、排查故障、给同事讲代理，回来翻它就够了。

PART


从直连说起：为什么要有个“中间人”

PROXY BASICS

互联网上最朴素的请求方式是客户端直连服务器：浏览器把请求发到服务器的 IP，服务器把响应原路返回，中间没有任何“转手”。

目标服务器

图 1：无代理直连，请求中间没有任何转手

但真实世界里，直连常常行不通：目标服务器不让你直接访问、公司要求所有上网行为留痕、后端服务多到一台机器扛不住……于是“代理”（Proxy）登场了。

代理的本质是一个“代劳者”：它接收你的请求，代替你去联系目标，再把结果回传给你。就像点外卖时的骑手——你不需要走进餐厅，骑手替你完成取餐与配送。

引入代理，有三个原始动机：

1

身份隐藏：服务器看不到真实请求者的身份与位置

2

访问控制：把流量收拢到一个统一入口，做权限与内容管控

3

性能加速：代理层做缓存、压缩、连接复用，为两端减负

关键认知：代理本身不生产内容，它只负责“转发”。而根据它站在谁的身边，演进出了两大流派——正向代理与反向代理。

正向代理：站在客户端身边

FORWARD PROXY

定义

正向代理（Forward Proxy）部署在客户端一侧（通常是内网出口），代理的是客户端——它以客户端的名义，代替客户端向外发起请求。

图 2：请求先经过正向代理，再被“代发”给目标服务器

请求流程

STEP 01

客户端发出请求

客户端把请求发给正向代理，目标地址写在请求里——代理知道你要去哪。

STEP 02

代理以自己身份转发

正向代理以自己的身份向目标服务器转发请求——服务器只看到代理的 IP，看不到真正的客户端。

STEP 03

目标服务器响应

目标服务器把响应返回给代理，而不是直接返回给客户端。

STEP 04

响应原路回传

代理把响应原样回传给客户端，请求闭环完成。

核心特性

关键就一句话：客户端知道目标是谁，目标不知道客户端是谁。


主动配置

代理站在请求方一侧，客户端必须主动配置代理地址，流量才会走它


部署位置

典型位置是公司内网出口、个人电脑、抓包工具

典型场景


访问受限资源

科学上网、内网穿透，绕开地理或网络限制


统一审计出口

公司要求员工必须走公司代理上网，日志留存、内容过滤


缓存加速

代理层缓存高频内容，内网重复请求不再出网


抓包调试

Charles、Fiddler 的本质就是正向代理——手机把代理指向电脑，流量一览无余

Nginx 正向代理配置演示

. . . nginx

# 正向代理:为内网客户端代理访问公网

server {

　　listen　　　 8080;　　# 内网客户端把 HTTP 代理指向这里

　　resolver　　 223.5.5.5;　# 由代理自己完成 DNS 解析

　　server_name　_;

　　location / {

　　　　# 关键:动态转发到请求里携带的目标主机

　　　　proxy_pass http://$http_host$request_uri;

　　　　proxy_set_header Host $host;

　　　　proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

　　}

}

配置完成后，内网机器的 HTTP 代理设置为192.168.1.5:8080，它访问外网的所有请求都会经过这台 Nginx 转发。

！踩坑提示 🕳

nginx 做正向代理，对 HTTPS 的 CONNECT 隧道支持并不完整，生产环境多为 Squid、Shadowsocks 等专业工具。这里拿 Nginx 演示，是让你用同一套工具看清“转发”的本质。

反向代理：站在服务器面前

REVERSE PROXY

定义

反向代理（Reverse Proxy）部署在服务器一侧（公网入口），代理的是服务器——它作为服务器的统一门面，替后端接受客户端的请求。

图 3：客户端只认 Nginx 一个入口，后端藏在门面之后

请求流程

STEP 01

请求打到“门面”

客户端以为自己在访问服务器，把请求发给反向代理——客户端只知道 Nginx 的域名，不知道后端的存在。

STEP 02

代理选择后端转发

反向代理按规则（权重、轮询、路径）选一台后端服务器，把请求转发过去。

STEP 03

后端返回响应

后端处理完业务，把响应返回给代理，而不是直接返回给客户端。

STEP 04

代理回传客户端

代理把响应回传给客户端，全程客户端都以为自己在直连服务器。

核心特性

同样一句话：客户端不知道后端是谁，后端也不知道客户端是谁——双方只认识 Nginx 这一个中间人。


零配置

代理站在服务方一侧，客户端无需任何配置，它以为自己在直连服务器


多后端分发

天然支持多台后端，一台 Nginx 把流量按权重分发给服务器集群

典型场景


负载均衡

一台 Nginx 分发到多台应用服务器，后端扩容只改配置


统一入口

HTTPS 证书、域名解析、路由规则集中在一处，后端只管业务


安全防护

隐藏后端真实 IP，集中做 WAF、限流、防攻击


动静分离

静态资源 Nginx 直接返回，动态请求转发后端，减轻应用压力


微服务网关

按路径分发到不同服务：/api/ 进订单服务，/pay/ 进支付服务

Nginx 反向代理配置演示

. . . nginx

# 1) 定义后端服务器组(负载均衡池)

upstream backend_servers {

　　server 192.168.1.10:8080 weight=3;　# 权重 3,承担更多流量

　　server 192.168.1.11:8080 weight=1;

　　server 192.168.1.12:8080 backup;　 # 备份节点,前两台不可用时启用

}

# 2) 反向代理入口

server {

　　listen　　　 80;

　　server_name　www.example.com;

　　location /api/ {

　　　　# 关键:把 /api/ 的请求转发给固定的后端服务器组

　　　　proxy_pass http://backend_servers;

　　　　proxy_set_header Host $host;

　　　　proxy_set_header X-Real-IP $remote_addr;

　　　　proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

　　　　proxy_set_header X-Forwarded-Proto $scheme;

　　}

}

当客户端访问www.example.com/api/xxx时，Nginx 会根据权重选择一台后端处理，并把客户端的真实 IP 通过X-Forwarded-For头传给后端。

一句话记住

正向代理“代客户寻路”，反向代理“替服务器迎客”

如果再简化一层，就只看方向：


正向 = 帮你访问别人

客户端主动把代理“夹”进请求链路


反向 = 帮别人接待你

服务器把代理“顶”在门前当门面

常见误区与选型建议

MISTAKES &； TIPS

误区一：Nginx 就是反向代理

Nginx 两种代理都支持——正向代理的配置你上面已经见过了。只是生产环境里反向代理用得多，印象才被固化。

误区二：走代理就等于加密

正向代理默认是明文转发，本身不做加密。想加密要靠代理支持 HTTPS CONNECT 隧道（或 TLS），别把“走代理”和“安全”划等号。

误区三：有了反向代理就不需要正向代理

两者场景不同，完全可以同时存在：公司出口一个正向代理管审计，应用入口一个反向代理管负载，互不冲突。

误区四：隐藏了后端，后端就不用防护

反向代理挡得住外部扫描，但挡不住应用层攻击（比如 SSRF 借代理探测内网）。后端该有的鉴权、校验、最小权限一个都不能少。

误区五：代理越多越安全

链路上的每个节点都是新的攻击面和故障点，该用一层就用一层，别为“显得专业”叠代理。

选型建议

1

想访问别人（流量出去）→ 用正向代理

2

想被别人访问（流量进来）→ 用反向代理

3

记忆锚点：正向代理是“代表你出门”，反向代理是“代表家迎客”。

WRAP UP

回顾全文，核心只有一句话：代理都是那个“代劳者”，区别只在于它替谁干活。

替客户端干活，站在请求出发的一侧，是正向代理；替服务器干活，站在请求到达的一侧，是反向代理。下次再遇到陌生的代理概念，先问一句：“它站在哪边？”——方向对了，一切都顺了。
